For each finding:

1. Change its status from `Open` to `In progress`.
2. Add a permanent regression test at the seam used by the audit reproduction.
3. Run the test and observe the reported failure.
4. Apply the smallest fix at the owning module boundary.
5. Run the focused test and the original user-flow scenario.
6. Run:

   ```sh
   mise exec -- pnpm --filter @stakekit/widget lint
   ```

8. Change the status to `Resolved` and record the fixing commit or PR.

Do not resolve a finding from inspection alone. The permanent regression test

## WAL-001 — Commands can route through the old wallet during enrichment

Severity: High
Status: Open
Confidence: High
Cross-validation: Earn/Classic investigator

### Behavior

Wallet core state can switch from owner/connector A to owner/connector B while
B still requires asynchronous enrichment. Until the complete enriched B
context emits, `WalletStateRuntime` continues publishing the completed A
context.

A new command started during this interval reads A and routes through A. The
audit reproduced this with a switch to a Cosmos connector whose public-key
enrichment was held pending.

### Evidence

- `packages/widget/src/services/wallet/wallet-state.ts:94-114` initializes one
  current context and replaces it only after the next complete context emits.
- `packages/widget/src/services/wallet/state-projection.ts:182-243` performs
  asynchronous Cosmos additional-address acquisition.
- `packages/widget/src/services/wallet/state-projection.ts:285-321` waits for
  the complete enriched projection before publishing it.
- `packages/widget/src/services/wallet/wallet-service.ts:49-80` reads the
  published context when a new message or transaction command starts.
- `packages/widget/src/services/workflow/transaction-workflow-runtime/signing.ts:87-118`
  validates against the same published Wallet State.
- `packages/widget/src/services/workflow/transaction-workflow-runtime/signing.ts:192-235`
  then dispatches signing through `WalletService`.

Observed twice:

```text
Expected routed connector: cosmos-uid
Received routed connector: first-uid
```

Classic Flow does not contain the race. Start/session guards and Transaction
Workflow validation both see stale owner A, so intake for A remains eligible.
When B eventually publishes, the route guard abandons the flow, but a wallet
operation that already captured A intentionally retains that context.

### Root cause

Optional/asynchronous enrichment and authoritative command routing share one
published context. An observed core identity change does not immediately make
the previous command context unavailable.

### Fix direction

Introduce a safe transition boundary when core owner or connector identity
changes. Viable designs include:

- immediately publishing a non-command-capable `connecting` state before
  enrichment;
- publishing the new owner synchronously and adding optional enrichment later;
  or
- comparing the routing context against the latest core snapshot immediately
  before every newly started command.

Do not interrupt a wallet operation merely because it was already in flight.
The fix must distinguish a command captured before the core transition from a
new command started after it.

### Acceptance criteria

- [ ] After core changes A to B, no new command can route through A.
- [ ] Classic and Borrow intake cannot start for stale owner A.
- [ ] Transaction Workflow validation cannot pass using stale owner A.
- [ ] A command captured before the core transition retains its documented
      routing context.
- [ ] Tests cover delayed Cosmos enrichment and delayed connector-chain
      enrichment.

## BOR-006 — Valid native collateral can crash risk derivation

Severity: High
Status: Open
Confidence: High

### Behavior

The decoded Borrow token model permits native collateral without a contract
address. Risk definition construction nevertheless calls `decodeTokenId` for
every collateral token. An absent address produces an invalid token ID such as
`ETH::` and throws synchronously.

The native token does not need to be selected. Its presence anywhere in the
markets used for risk derivation can crash the Borrow dashboard projection.

### Evidence

- `packages/widget/src/domain/borrow/token.ts:5-8` makes the token address
  optional.
- `packages/widget/src/domain/borrow/ids.ts:50-63` requires the address portion
  of `TokenId` to be a non-empty `TokenAddress` and substitutes an empty string
  when the address is absent.
- `packages/widget/src/domain/borrow/risk-position.ts:186-204` decodes a token
  ID for every collateral definition without handling a native token.

Observed:

```text
decodedNativeAddress = null
Expected a value with a length of at least 1, got ""
at TokenId part [2]
```

### Root cause

The Borrow token schema and the domain identity model disagree about whether a
collateral token may be addressless.

### Fix direction

Define one canonical native-token identity in the Borrow domain. Do not use an
empty address as an implicit sentinel. Decode valid native collateral into that
identity before risk composition.

### Acceptance criteria

- [ ] A valid native collateral token decodes into a stable `TokenId`.
- [ ] A market containing native collateral cannot throw during risk
      construction.
- [ ] Addressed and native tokens cannot collide.
- [ ] Risk can return available or typed-unavailable for native collateral.
- [ ] Permanent fixtures cover a native token that is present but not selected.

## BOR-007 — Precision loss can bypass known-capacity blocking

Severity: Medium
Status: Open
Confidence: High

### Behavior

Borrow form amounts use `BigNumber` and the Action Command retains the exact
decimal string. Before risk assessment, the amount is converted to a JavaScript
`number`.

The audit borrowed `0.10000000000000001` against capacity `0.1`. Conversion
rounded the assessment input to `0.1`; preparation returned `Ready` even though
the exact command amount exceeded known capacity.

### Evidence

- `packages/widget/src/features/borrow/model/action-preparation.ts:512-535`
  converts borrow and collateral amounts with `.toNumber()`.
- `packages/widget/src/features/borrow/model/action-preparation.ts:657-663`
  uses the same conversion for repayment.
- `packages/widget/src/domain/borrow/risk-position.ts:478-494` blocks only when
  the numeric projection exceeds capacity.

Observed:

```text
exactAmount = 0.10000000000000001
numberGivenToRiskModel = 0.1
riskCapacityUsd = 0.1
preparation = Ready
```

Supply, repay, and withdraw changes use the same number-based risk model and
require equivalent boundary coverage.

### Root cause

Transaction intent and risk eligibility use different numeric domains. The
command is exact; the safeguard is binary floating-point.

### Fix direction

Keep action amounts and risk arithmetic in an exact decimal representation
through assessment and comparison. Convert only at display or external
boundaries that explicitly require a number.

### Acceptance criteria

- [ ] Exact amounts above capacity are blocked.
- [ ] Exact amounts equal to capacity retain the intended boundary behavior.
- [ ] The risk model and Action Command use equivalent precision.
- [ ] Borrow, supply, repay, withdraw, and collateral-toggle projections have
      precision-boundary tests.

## BOR-008 — Pool repayment mixes market-local and account-wide debt

Severity: Medium
Status: Open
Confidence: High

### Behavior

For pool integrations with debt in multiple markets, repayment Review shows
the current debt from the selected market but the projected debt from the
account-wide Risk Position.

The audit modeled `$1,000` account debt, `$400` debt in the selected market, and
a `$100` repayment. Review displayed `$400 → $900`, making debt appear to
increase after repayment.

### Evidence

- `packages/widget/src/features/borrow/model/action-preparation.ts:637-679`
  derives current debt from `debtBalance.balanceUsd` and projected debt from
  `position.risk.assess(...).projection.totalDebtUsd`.
- `packages/widget/src/features/borrow/model/action-preparation.ts:717-728`
  passes those mixed-scope values into the immutable Review facts.

Observed:

```text
existingDebtUsd = 400
repayUsd = 100
projectedDebtUsd = 900
```

### Root cause

The two sides of one Review transition use different financial scopes:
market-local current debt and account-wide projected debt.

### Fix direction

Choose one semantic scope for the Review transition:

- account-wide: `$1,000 → $900`; or
- market-local: `$400 → $300`.

The Review copy and type should make the selected scope explicit.

### Acceptance criteria

- [ ] Existing and projected debt in one Review row use the same scope.
- [ ] Multi-market pool repayment shows a decreasing debt transition.
- [ ] Isolated-market repayment remains market-scoped.
- [ ] Repay-all and partial-repay paths use the same rule.

## BOR-009 — Additional-address changes reset Borrow dashboard intent

Severity: Medium
Status: Open
Confidence: High

### Behavior

Wallet enrichment that changes only additional addresses creates a different
Borrow form Atom-family key. The dashboard silently loses selected market,
selected collateral, and entered amounts.

This contradicts the Wallet Scope Owner rule in `CONTEXT.md`: additional
addresses do not change ownership. Case-only EVM address changes can produce
the same state-keying problem.

### Evidence

- `packages/widget/src/features/borrow/state/form.ts:40-56` keys form state by
  a complete `WalletScopeKey`.
- `packages/widget/src/features/borrow/state/form.ts:105-109` builds that key
  from the current dashboard scope.
- `packages/widget/src/features/borrow/state/form.ts:145-155` rebuilds the
  dashboard key whenever full scope equality changes.
- `packages/widget/src/features/borrow/model/borrow-form.ts:110-120` defines
  the full-scope dashboard key and zero-value defaults.

Observed:

```text
before.borrowAmount = 25
before.collateralAmount = 1
after.borrowAmount = 0
after.collateralAmount = 0
```

### Root cause

Presentation intent is owned by the full resource-request identity rather than
the Wallet Scope Owner.

### Fix direction

Key Borrow dashboard intent by `WalletScopeOwnerKey`. Continue keying remote
balance requests by the complete scope when additional addresses affect the
request.

### Acceptance criteria

- [ ] Additional-address enrichment preserves dashboard intent.
- [ ] Case-only EVM address changes preserve dashboard intent.
- [ ] Primary address or network changes reset dashboard intent.
- [ ] Remote balance resources still react to additional-address changes.

## BAL-001 — Current balance scope can miss workflow invalidation

Severity: Medium
Status: Open; independently reconfirmed
Confidence: High
Cross-validation: Borrow investigator

### Behavior

A Transaction Flow captures an immutable full Wallet Scope. Additional-address
changes do not invalidate the Flow Session, so the current token-balance
resource can move to a new full scope while execution continues.

Submission and completion invalidate the captured old scope only. The current
resource is not refreshed.

### Evidence

- `packages/widget/src/services/resource-invalidation.ts:10-14` stores a full
  `WalletScopeKey` in `WalletBalancesInvalidationKey`.
- `packages/widget/src/services/resource-invalidation.ts:88-90` constructs
  exact full-scope wallet-balance invalidation keys.
- `packages/widget/src/services/workflow/transaction-workflow-operations-service.ts:11-25`
  derives completion invalidations from the captured workflow input.
- `packages/widget/src/resources/token-balances/token-balances.ts:38-58`
  subscribes each exact full-scope balance resource to its matching key and
  otherwise refreshes on a one-minute schedule.
- `packages/widget/src/features/borrow/ui/borrow-layout.tsx:18-38` keeps the
  Borrow details pane mounted across Review, Steps, and Complete.

Observed:

```text
captured old-scope request count after invalidation = 2
current new-scope request count after invalidation = 1
```

Borrow positions and markets use owner/network invalidation and can refresh
while the mounted wallet balance remains stale. This can leave collateral
balance, Max, and wallet-balance validation stale for approximately one minute.

### Root cause

The flow lifetime uses Wallet Scope Owner semantics, while balance invalidation
uses one captured full-scope identity.

### Fix direction

Either:

- invalidate all balance resources for the Wallet Scope Owner; or
- invalidate both the captured affected scope and the current live scope.

The design must preserve complete-scope request identity while avoiding stale
variants for the same owner.

### Acceptance criteria

- [ ] Completion refreshes the currently mounted balance resource.
- [ ] The captured affected scope is also refreshed when still cached.
- [ ] Other wallet owners and networks are not refreshed.
- [ ] Borrow does not show fresh positions with stale wallet balances.
- [ ] Regression coverage changes only additional addresses during execution.

## POS-003 — Exit starts without required validator arguments

Severity: Medium
Status: Open
Confidence: High

### Behavior

Position Exit can start Classic Review when the selected yield requires a
validator argument but no validator can be derived from the balance.

The resulting immutable Action Command omits the required singular argument or
contains an empty required plural array. The user reaches Review with intake
that cannot create a valid Action Preview.

### Evidence

- `packages/widget/src/features/position-details/state/classic-flow-actions.ts:87-100`
  returns `validatorAddresses: []` when the required plural value is absent.
- `packages/widget/src/features/position-details/state/classic-flow-actions.ts:101-123`
  returns `{}` when the required singular value is absent.
- `packages/widget/src/features/position-details/state/classic-flow-actions.ts:153-172`
  treats either object as prepared and starts Classic Transaction Flow.

Observed navigation:

```text
/positions/ethereum-eth-native-staking/default/unstake/review
```

Expected behavior was no Flow Session and no navigation.

### Root cause

Missing required validator data is represented as a valid empty argument object
instead of unavailable preparation.

### Fix direction

Return `null` or a typed blocked preparation whenever a required singular or
plural validator value cannot be derived. Keep subnet validation aligned with
the same rule.

### Acceptance criteria

- [ ] Required singular validator absence cannot start Review.
- [ ] Required plural validator absence cannot start Review.
- [ ] Optional validator arguments may remain absent.
- [ ] Required subnet absence remains blocked.
- [ ] Tests exercise the real position-exit Start command.

## ACT-003 — Activity Resume accepts another action type's route

Severity: Medium
Status: Open
Confidence: High

### Behavior

A STAKE Activity Resume Flow Session considers
`/activity/unstake/steps` active. The inverse mismatch is possible for other
action types.

Browser or host navigation can therefore keep one action's session and
workflow mounted beneath another action type's execution route.

### Evidence

- `packages/widget/src/features/classic-transaction-flow/state/classic-transaction-flow.ts:94-116`
  validates the `/activity` prefix and terminal `steps`/`complete` segment but
  does not compare the action-type segment.
- `packages/widget/src/features/classic-transaction-flow/state/classic-transaction-flow.ts:245-250`
  publishes this predicate as the active Flow Session path.
- `packages/widget/src/app/routes/classic-routes.tsx:32-50` uses the result to
  preserve the route lifetime key.

Observed:

```text
Session action type: STAKE
Path: /activity/unstake/steps
isActiveClassicTransactionFlowPath = true
```

### Root cause

Activity Review uses `/activity/review`, while Steps and Complete insert a
dynamic action segment. The custom matcher checks the shape but not the
session's expected segment.

### Fix direction

Compare against the session's exact destination paths, or derive and validate
the expected action segment from `stepsPath` and `completePath`.

### Acceptance criteria

- [ ] STAKE accepts only STAKE execution paths.
- [ ] UNSTAKE accepts only UNSTAKE execution paths.
- [ ] Pending/other Activity types accept only their own paths.
- [ ] Review, Steps, and Complete still share one valid Flow Session lifetime.
- [ ] Host and browser navigation to a mismatched route abandons the session.

## NAV-001 — Failed deep-link navigation is permanently claimed

Severity: Low
Status: Open
Confidence: High

### Behavior

Pending-action validator-selection and plain position deep links update their
claimed-intent state before executing navigation. If the router rejects that
navigation, later readiness changes see the intent as consumed and do not retry.

### Evidence

- `packages/widget/src/app/routes/state/pending-action-deep-link-route.ts:102-106`
  claims a pending-action intent before `runWidgetNavigationCommand`.
- `packages/widget/src/app/routes/state/pending-action-deep-link-route.ts:123-136`
  uses the same ordering for plain position deep links.
- The branch at `packages/widget/src/app/routes/state/pending-action-deep-link-route.ts:88-99`
  demonstrates the safer pattern of committing claim state only after a
  successful Flow Start outcome.

Observed after an injected first navigation failure and a readiness retrigger:

```text
expected pushCalls = 2
received pushCalls = 1
```

### Root cause

Claim state represents an attempted side effect rather than a successfully
accepted destination.

### Fix direction

Commit the claim only after navigation succeeds, or roll it back on failure.
Keep the existing deduplication behavior after success.

### Acceptance criteria

- [ ] Failed pending-action navigation can retry.
- [ ] Failed plain position navigation can retry.
- [ ] Successful navigation remains one-shot.
- [ ] Repeated readiness emissions do not duplicate successful navigation.

## WAL-002 — EVM address casing duplicates connection tracking

Severity: Low
Status: Open
Confidence: High

### Behavior

Wallet lifecycle memory builds its identity key from the address string without
EVM normalization. Emitting lowercase and checksum casing for the same EVM
owner records two `connectedWallet` events.

### Evidence

- `packages/widget/src/services/wallet/lifecycle.ts:24-43` builds
  `trackedConnection` from the raw address.
- `packages/widget/src/services/wallet/domain/scope.ts:55-77` defines the
  application-wide owner rule: EVM addresses compare case-insensitively.

Observed:

```text
expected connectedWallet calls = 1
received connectedWallet calls = 2
```

The unsupported-connection memory at
`packages/widget/src/services/wallet/lifecycle.ts:46-59` uses the same
case-sensitive address pattern.

### Root cause

Lifecycle deduplication defines wallet identity differently from Wallet Scope
Owner.

### Fix direction

Build lifecycle identity from `walletScopeOwnerKey` or the same canonical owner
normalization used by Wallet Scope.

### Acceptance criteria

- [ ] Lowercase/checksum EVM variants produce one connection event.
- [ ] Different EVM owners still produce distinct events.
- [ ] Non-EVM address comparison remains case-sensitive.
- [ ] Unsupported-connection deduplication uses the same identity rule.

## Unconfirmed risk

`packages/widget/src/domain/borrow/risk-position.ts:331-366` identifies
collateral changes by token ID and updates every matching exposure.

If a pool account can validly contain the same collateral token across multiple
market balances, one withdrawal could adjust more than the intended exposure.
The generated API contract and available fixtures do not establish whether
that state is valid. This is not classified as a bug until a first-party API
fixture or contract confirms the scenario.

## Explicitly falsified candidates

- Delayed replacement Start did not allow stale navigation to win. Effect
  Atom's non-concurrent command behavior and epoch-aware cleanup suppressed it.
- Double Start did not produce a confirmed Borrow defect.
- Returning through Borrow Review/Steps history did not revive a disposed
  Transaction Workflow in existing coverage.

## Coverage gaps

- No live API environment or real wallet/connector signing was exercised.
- The confirmed findings were reproduced at deterministic model, Atom, resource,

- Temporary audit harnesses were removed; permanent regression tests do not yet

  exact-decimal capacity boundaries, and additional-address changes during a
  routed transaction.
- Arbitrary host-driven routing and transient Application Router failure have

- The test suite's Cosmos lazy-loading test is sensitive to full-suite
