# Effect-native modules own application orchestration

Plain TypeScript owns deterministic decisions. Effect-native modules own multi-step orchestration, concurrency, retries, rollback, typed failures, and scoped lifetimes. Effect Atoms own reactive composition, feature-local state, and adaptation between React, Authoritative Resources, and Effect-native modules.

A command Atom may read the current reactive snapshot and invoke one semantic Effect operation. It does not coordinate a workflow through registry subscriptions, manual refresh-and-wait loops, rollback writes, or chains of command Atoms. Lifecycle Atoms may acquire a scoped Effect-native module, publish its observable state reactively, invoke semantic operations, and release it when the owning lifecycle ends.

Feature-specific orchestration remains owned by its feature and is implemented without Atom dependencies while consuming Effect capabilities from the application or wallet runtime. `src/services` owns reusable capabilities and workflow engines whose interfaces are independent of features and Authoritative Resources. A feature-owned orchestration module moves into `src/services` only when its concepts and dependencies have genuinely become service-owned; `src/services` is not a generic destination for important application logic.

Scoped orchestration follows the domain lifecycle rather than collapsing related phases into one nullable controller. A Transaction Flow has one scoped Session module per Flow Session, one scoped Review module per Review scope, and one scoped Execution module per Execution Attempt. The route tree is authoritative for these child lifetimes because browser navigation, host routing, redirects, and guards may change routes without passing through an Effect navigation operation. One root lifecycle Atom per route scope encapsulates the complete acquisition, state observation, and release sequence; callers do not mount handle or state atoms individually. This preserves the fresh Review and fresh Execution rules of ADR-0005 and ADR-0006 while moving their orchestration out of the Atom graph.

The Effect service and its scoped handles expose intention-revealing operations such as Start, acquire Review, Confirm, Back, and Finish rather than a generic tagged-command `dispatch` interface. Tagged commands, serialization, ordering, and stale-ownership checks remain private implementation machinery. Each operation returns a typed semantic outcome or fails with a typed operational error, and Atom commands map one-for-one onto those operations without coordinating several lifecycle operations themselves.

The owning Effect-native module directly invokes navigation, tracking, resource invalidation, operation capabilities, and other side effects required by an accepted transition. It does not emit imperative instructions for an Atom to interpret. Events communicate semantic facts to observers; they are not an instruction bus that preserves Atom-owned orchestration in another form.

Effect-native orchestration interfaces never accept or return an `Atom`, `AtomRegistry`, `AtomContext`, or `FnContext`. Atom adapters resolve Authoritative Resources and current feature state into normalized values or read-only Effect streams. Tests of the orchestration module therefore use its production interface and Effect Layers without reproducing Atom registry setup, mount ordering, or subscription choreography.

Inputs are classified by their lifetime. Facts invariant for a scope, including immutable Flow Session intake and its captured Wallet Scope, are constructor input. Volatile facts needed only to evaluate a user command are normalized into that command and revalidated by the module. A fact whose change must autonomously interrupt or invalidate the scope may be supplied as an explicitly typed read-only Effect Stream; this is an exceptional semantic dependency, not a generic live-application-state channel.

Classic Review receives one normalized eligibility Stream from its Atom bridge because KYC and Activity-expiry facts remain owned by Authoritative Resources while their changes autonomously drive Review behavior. The Review implementation owns preview-start and confirmation policy in response to that Stream; it does not acquire or recreate Atom-owned resource machinery. Eligibility remains private consumed state rather than being republished through the Review state Stream, whose observable facts are limited to state uniquely owned by Review such as Action Preview loading, success, and failure.

Review exposes one deep Confirm operation rather than separate Preview retry and promotion operations. Confirm ensures a valid Action Preview exists, applies the existing retry policy for retryable Preview failures, reserves the action, records required tracking, and navigates with rollback on failure. Atom and UI callers do not sequence these steps.

The route-scoped Review handle exposes only its Action Preview state Stream and Confirm. It has no generic state object, event Stream, separate retry operation, or tagged-command dispatcher.

The route-scoped Execution handle exposes only the Transaction Workflow state Stream, one operation accepting the existing semantic `TransactionWorkflowCommand` union, and explicit Back and Finish operations. Each operation returns Accepted or Rejected Stale so a Wallet Scope or replacement race is observable, while navigation failures remain in the Effect error channel. Completion observation and retrying completion navigation are automatic scoped behavior. Execution has no event Stream, generic Flow dispatcher, public ownership check, or exposed action handoff.

Operation eligibility is represented separately from operational failure. Expected ineligibility returns a typed outcome such as an accepted result, a semantic rejection reason, or stale ownership. Operational problems use the typed Effect error channel. Broken invariants and impossible states remain defects. Operations do not silently return `void` for meaningful rejection, and callers do not infer rejection by inspecting exceptions or incidental state.

Each workflow fact has one authoritative writer. State owned by a scoped Effect-native module remains authoritative there; an Atom may publish a passive reactive mirror or pure projection but cannot maintain an independently writable copy of the same fact. Atoms remain authoritative for feature-local synchronous intent, selection, presentation state, and resource binding that is outside the orchestration module's lifecycle.

Feature `model/` modules are deterministic and cannot import Effect Atom or depend on an Atom registry or context reader, including through type-only dependencies. State adapters first resolve resources into explicit normalized observations and then invoke pure constructors, reducers, eligibility functions, and projections. Pure Effect data types and combinators remain valid model dependencies; reactive reads and Effect execution do not.

A command Atom may normalize input and tail-delegate to exactly one public semantic command Atom owned by another feature, then map its typed outcome. It cannot coordinate commands before and after that delegation, mutate several stores, subscribe, retry, or implement rollback. Collaboration requiring more than one semantic step belongs in a neutral parent orchestration module or reusable capability rather than a longer Atom command chain.

A command Atom has a deliberately small complexity budget: it may read the current reactive snapshot, invoke a pure decision or normalization function, and then perform exactly one local authoritative state transition, one scoped-handle operation, or one permitted cross-feature tail delegation before mapping the typed result. It cannot directly access the registry, subscribe, mount, refresh-and-wait, retry, coordinate multiple command Atoms, or implement compensating writes. Lifecycle Atoms are the explicit exception for acquiring, observing, and releasing scoped handles.

Tests move with the seam rather than accumulating around both architectures. Deterministic decisions are tested directly with values. Effect-native orchestration is tested through the production service's semantic operations and observable state using its real layer, scoped execution, and test adapters for external capabilities. Session, Review, and Execution implementation factories are not independent behavior-test surfaces. Atom adapter tests cover service lookup, route-scope acquisition and release, reactive publication, and operation forwarding only. Registry-heavy workflow tests and direct phase-factory tests are removed once equivalent behavior is covered through the service interface, while a small number of integration and browser tests retain end-to-end journey coverage.

Migration proceeds as feature-complete vertical slices. Classic Transaction Flow establishes the reference implementation, followed by Borrow Transaction Flow, Yield Entry submission, Earn resource-observation separation, and then an audit of remaining command Atoms. Each slice replaces its old implementation and behavior tests before the next begins. No generic Flow abstraction is introduced from Classic alone; shared structure is extracted only after Classic and Borrow demonstrate a genuinely common interface or implementation.

Architecture tooling enforces only mechanically reliable invariants, introduced as each slice removes the corresponding existing violations: feature `model/` modules cannot import Effect Atom, production module interfaces cannot expose Atom registry or context types, direct registry access is confined to declared lifecycle adapters, and existing dependency-direction checks remain authoritative. The semantic command-Atom complexity budget remains a review rule unless it can be expressed without false positives or broad suppressions.

These migrations preserve behavior by default. Existing Flow Session, Review, and Execution Attempt semantics, navigation commands, tracking, invalidation, retry eligibility, stale-owner handling, and user-visible failures are characterized and retained. Defects discovered during extraction are recorded and fixed separately unless they prevent a safe implementation of the new seam.

Observable channels are demand-driven. A state Stream is exposed only when a reactive production consumer needs authoritative changing facts, and a one-off semantic result is returned directly from the operation that produced it. An event Stream is introduced only for a real production observer that cannot use state or an operation outcome; tests alone do not justify it. Required navigation, tracking, invalidation, and handoffs execute inside the owning module rather than through an event instruction bus.

The existing Transaction Workflow event Stream and its Atom projection have no production observer and are removed during the Classic redesign. Transaction Workflow tests assert authoritative state and operation effects rather than retaining a production event channel solely as a test probe.

Operation concurrency belongs to the Effect-native module. Operations are serialized by default, and duplicate or ineligible operations return typed outcomes based on current module state. Coalescing, dropping, or parallel execution requires an explicit per-operation policy. Correctness cannot depend on an Atom command's `concurrent: false` setting; Atom adapters only invoke semantic operations and project waiting state for presentation.

A private reusable scoped-serialization module under neutral `src/shared/effect` infrastructure owns the identical semaphore, scope-closure, interrupt-on-close, and finalization mechanics used by lifecycle operations. It does not encode Flow Session state, owner validation, action handoff, navigation, tracking, or other Transaction Flow policy. Classic establishes this infrastructure in its vertical slice; the later Borrow slice adopts it only if Borrow demonstrates the same mechanics, while keeping journey policy in a separate implementation.

Releasing a lifecycle module interrupts its owned fibers and closes its queues and streams. Finalization is idempotent, in-flight and queued operations are interrupted, and required rollback remains private implementation. Scope closure is not a public semantic outcome; Atom adapters release the handle but do not perform additional workflow cleanup or state repair. Completed external side effects are not implicitly compensated, and stale shared-world outputs remain suppressed according to the existing Flow Session and Execution Attempt rules.

A successfully created lifecycle handle's state Stream emits its complete initial state immediately. Scoped Atom adapters represent handle acquisition explicitly, normally as an `AsyncResult`, and do not fabricate Review or Transaction Workflow state while acquisition is pending. React may project that acquisition state into an existing loading or skeleton view. Consumers do not issue a separate initialization command, reconstruct initial lifecycle state, or maintain a writable state mirror. Invalid constructor input or dependency acquisition fails the scoped factory through its typed Effect error channel; operational loading and retryable failure states occur only after successful construction and are published by the module.

Migrated feature internals make the seam visible: `model/` contains deterministic logic, `state/orchestration/` contains Atom-independent Effect-native modules, `state/atoms/` contains lifecycle and reactive adapters, and the root `state.ts` remains the narrow public feature interface. This layout is adopted during each vertical slice rather than through an unrelated repository-wide file move. The folder is named `orchestration` rather than `workflow` because Transaction Workflow already has a precise domain meaning.

A narrow internal Effect-to-Atom lifecycle adapter under `src/app/runtime` owns the repeated acquisition, keep-alive, optional state-stream projection, and release sequence for a scoped Effect handle. Session, Review, and Execution in Classic provide multiple concrete consumers for this seam. The later Borrow vertical slice adopts the adapter for equivalent scoped Effect handles only if its migrated interface demonstrates the same lifecycle; this Classic slice does not add dummy Effect handles or partially migrate Borrow merely to manufacture another consumer. The adapter contains no Transaction Flow commands, navigation, eligibility, or domain outcomes; feature adapters remain responsible for their semantic projections and operations, and a generic type alias by itself provides insufficient leverage.

Published feature facades remain stable during internal migration wherever they already satisfy ADR-0011. Existing view Atoms, command Atoms, and zero-logic hooks retain their names and value shapes by default, while internal command outcomes may become more precise without exposing orchestration machinery to UI consumers. An interface that leaks dynamic Atoms, registry context, or orchestration machinery changes with every consumer in the same vertical slice; no temporary compatibility facade survives the slice solely to preserve a prohibited interface.

Feature-owned orchestration services remain private implementation and are not exported from a feature's root `state.ts`. Cross-feature consumers continue through the narrow published Atom facade, which binds semantic service operations to the current Widget Instance and preserves feature import rules without exposing Session acquisition or lifecycle machinery.

The application runtime composition root is the sole privileged importer of a private feature orchestration service for layer wiring. `app/runtime/wallet-runtime.ts` may import the exact `ClassicTransactionFlowService` module, enforced by an exact-file rev-dep allowlist; no other app module or feature receives that exception. Runtime composition does not become a fourth feature entry and the service remains absent from `state.ts`.

Authoritative Resources retain their existing Atom ownership of reactive caching, polling, pagination, retry policy, stale-result suppression, and registry-scoped resource lifetimes. Those responsibilities are intrinsic to the resource module and are not migrated into feature orchestration modules. The new command-Atom restrictions prevent features from reimplementing resource policy or coordinating refresh-and-wait sequences; they do not prohibit lifecycle and resource Atoms from using the Atom machinery required by their ownership.

An orchestration-heavy feature exposes one Effect service as its external seam. The code-level `ClassicTransactionFlowService` is eagerly constructed once per Wallet Runtime by that runtime's scoped layer and remains alive independently of route mounts. Its implementation directly owns the active Flow Session, epoch allocation, Wallet observation, Start, abandonment, and Session acquisition. Session, Review, and Execution remain private scoped implementation modules rather than separately composed `Context.Service` definitions; their dynamic session, action, and eligibility inputs are supplied when the corresponding child scope is acquired.

Layer construction resolves every static Effect dependency and the implementation closes over the resulting concrete adapters. Flow operations do not use local `Effect.provideService` calls to reintroduce dependencies already resolved during construction. Values that genuinely vary by child scope, such as the Flow Session, Action Preview eligibility Stream, or execution action, remain explicit operation inputs rather than Effect services.

Navigation command interpretation belongs to the `WidgetNavigation` service interface rather than an app-runtime helper. The resolved navigation adapter accepts the closed Back, Push, and Replace command union directly, so feature orchestration neither switches over navigation operations nor re-provides `WidgetNavigation` while an operation is running. The previous `app/runtime/navigation.ts` helper is removed in this slice; non-Classic consumers move mechanically to the service-owned command type and operation without otherwise migrating their orchestration.

The parent Session module supplies private semantic capabilities to its child Review and Execution factories for lifecycle handoffs, ownership checks, and cleanup. Child operations use those capabilities internally as part of one accepted transition. An Atom never invokes a child operation and then separately repairs or advances parent state. These parent-child capabilities are internal seams of the Session implementation, not public feature capabilities or Atom callbacks.

The Session's reserved execution action is private implementation state rather than an observable state Stream. Review invokes one private `promoteToExecution` capability that verifies current ownership, rejects duplicate reservation, reserves the action, navigates to Steps, and rolls back only that reservation on navigation failure or interruption. The Execution route calls `acquireExecution` and receives a tagged Acquired, Rejected No Reservation, or Rejected Stale outcome. These expected acquisition results stay in the success channel; the Effect error channel is reserved for operational construction failures. The Atom bridge never reads, mirrors, or compares the reserved action.

The route-scoped Session handle visible to the Atom bridge exposes only immutable intake plus `acquireReview` and `acquireExecution`. Current-ownership checks, epoch comparison, execution reservation and rollback, Session clearing, and navigation handoff are private closures supplied by the service implementation to its child modules.

The active Flow Session store is authoritative in the feature-owned Effect service rather than in writable Atoms. Starting selects a fresh Flow Session and monotonic local epoch, replacement makes the previous Session stale, and Session modules receive private current-ownership capabilities from the service implementation. The Atom facade passively publishes the current Session for routing and invokes semantic operations, while a scoped Session handle clears only its captured Session during release so an overlapping exiting route tree cannot mutate a replacement.

`ClassicTransactionFlowService` exposes the current Flow Session as its only observable top-level state. Its epoch counter, serialization machinery, and lifecycle flags remain private. Start returns the accepted Session, while Session acquisition and Dashboard Activity Resume abandonment receive the captured Session so a stale route or click cannot affect a replacement.

Classic and Borrow retain separate Flow services with journey-specific intake, state, operations, outcomes, and lifecycle rules. A union-heavy global Transaction Flow service is not introduced. Further shared construction may be considered only after both implementations demonstrate genuinely identical machinery.

Starting one journey does not directly clear or command the other journey's service. Routing and each journey's lifecycle end the previously presented scope. A future product requirement for one active Flow Session across all journey types would require a separate application-level owner and decision rather than incidental coupling between the two feature services.

Flow services consume `WalletService.state` and `WalletService.states` directly through the wallet runtime. Start validates against the current normalized Wallet Scope, and the service observes wallet states to invalidate a Session whose owner becomes ineligible. The service's current-session state is the sole authority for owner eligibility; route guards may check route and intake-variant compatibility but do not independently revalidate Wallet Scope ownership. Atom wallet projections are not fed back into orchestration, and journey-specific owner rules remain deterministic model functions.

Navigation-bound transitions reserve their new Session or execution handoff before invoking navigation. Every explicit Start still creates a fresh Session and epoch, including equal intake, so a later serialized Start intentionally replaces the prior attempt. Concurrent duplicate execution promotions observe the reserved action and are rejected. A navigation failure rolls back only when the same Session or action still owns the reservation, and it returns a typed operational failure. A stale failed command never clears a newer replacement.

Completion navigation retains its existing retry schedule during migration: the Execution module retries every 100 milliseconds until navigation succeeds or its scope is interrupted. Tests drive this policy with `TestClock`. Replacing it with bounded retries or a user-visible navigation failure is a separate product decision rather than part of the orchestration migration.

Outputs are classified by ownership. UI-ownership outputs such as navigation, active-session cleanup, and presentation outcomes require current Session or Execution ownership and are suppressed once stale. Transaction-truth outputs such as tracking an operation that occurred and invalidating facts changed by a real transaction execute once even if the presenting scope has become stale. Staleness does not suppress every output indiscriminately.

A vertical slice is complete only when its orchestration modules have no Atom dependencies, its command Atoms satisfy the complexity budget, and its `model/` modules are deterministic; interface-level Effect tests cover transitions, failures, concurrency, staleness, and cleanup; adapter tests cover only reactive wiring and lifecycle; replaced registry-heavy implementation and behavior tests are removed; relevant automated architecture checks are enabled; lint, hygiene, targeted tests, and affected browser tests pass; and no temporary migration interface remains in the published facade.

This refines ADR-0004: Effect and Effect Atom still jointly own application behavior outside React, but they have distinct responsibilities. Keeping all orchestration in Atoms was rejected because Atom registry timing and identity become part of the workflow interface and tests must reproduce internal mount, subscription, and command choreography. Moving deterministic decisions or reactive composition into Effect services was rejected because it adds ceremony and obscures the natural test seam.
